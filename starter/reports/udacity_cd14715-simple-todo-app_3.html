Quality Issues

  • CRITICAL / security / Line 17

    PaymentDetails interface stores sensitive card data (cardNumber, CVV) as plain strings without encryption or secure handling. This violates PCI DSS requirements and exposes card data throughout the application lifecycle.

    Fix: Never store or transmit full card numbers or CVV in application code. Use a PCI-compliant payment gateway (Stripe, PayPal) that provides tokenization. Replace PaymentDetails with: `interface PaymentDetails { paymentToken: string; amount: number; }` and obtain tokens from the gateway's client-side SDK.

  • CRITICAL / bug-risk / Line 95

    Money calculation uses floating-point arithmetic (9.99 * 0.08), which causes precision errors in financial calculations. For example, 9.99 + (9.99 * 0.08) + (9.99 * 0.029) may not equal exactly 10.279 due to binary floating-point representation.

    Fix: Use integer arithmetic with cents: `const PRICING = { premium: 999, enterprise: 4999 }; const basePrice = PRICING[tier]; const tax = Math.round(basePrice * TAX_RATE); const fee = Math.round(basePrice * PROCESSING_FEE); return basePrice + tax + fee;` and document that amounts are in cents. Alternatively, use a decimal library like decimal.js.

  • HIGH / bug-risk / Line 45

    Payment processing (chargeCard) and subscription upgrade (upgradeUserSubscription) are executed sequentially without transaction management. If upgradeUserSubscription fails after chargeCard succeeds, the user is charged but not upgraded, causing financial discrepancy and customer disputes.

    Fix: Wrap both operations in a database transaction: `await db.beginTransaction(); try { await chargeCard(...); await upgradeUserSubscription(...); await db.commit(); } catch (err) { await db.rollback(); throw err; }` Or use a payment gateway webhook to upgrade subscriptions only after confirmed payment.

  • HIGH / bug-risk / Line 115

    chargeCard returns boolean (true/false) hiding the actual failure reason. When payment fails, the caller cannot distinguish between network errors, insufficient funds, invalid card, or database failures, making debugging and user feedback impossible.

    Fix: Return a typed result: `type PaymentResult = { success: true; transactionId: string } | { success: false; error: 'network_error' | 'card_declined' | 'database_error'; message: string };` Then callers can provide specific error messages to users and log appropriate details.

  • HIGH / security / Line 124

    Payment error logged to console.error may expose sensitive payment details in logs. The error object could contain card information, user IDs, or database connection strings visible in production log aggregation systems.

    Fix: Remove console.error or sanitize the error before logging: `const safeError = { message: error instanceof Error ? error.message : 'Unknown error', timestamp: new Date() }; logger.error('Payment processing failed', safeError);` Never log the raw error or payment object.

  • HIGH / security / Line 65

    Card number validation only checks length === 16, accepting any 16-character string including '0000000000000000' or 'abcd1234efgh5678'. No validation that characters are digits or that the number passes Luhn checksum algorithm.

    Fix: Add proper validation: `if (!/^\d{13,19}$/.test(cardNumber)) return false; // Luhn algorithm: let sum = 0; let isEven = false; for (let i = cardNumber.length - 1; i >= 0; i--) { let digit = parseInt(cardNumber[i], 10); if (isEven) { digit *= 2; if (digit > 9) digit -= 9; } sum += digit; isEven = !isEven; } if (sum % 10 !== 0) return false;`

  • MEDIUM / bug-risk / Line 82

    Fix: Always specify radix 10: `const [month, year] = expiryDate.split('/'); const expiryDateObj = new Date(2000 + parseInt(year, 10), parseInt(month, 10) - 1);`
